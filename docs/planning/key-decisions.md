## 1. 출시 목표일과 MVP 범위

**왜 먼저인가:** 남은 기간은 39일이고 개발자는 1명이다. 출시일이 정해져야 나머지 기능의 포함 여부를 판단할 수 있다. 롤링페이퍼는 크리스마스 전에 메시지가 쌓일 시간이 필요하다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 12월 초 출시 (약 2~3주 개발) | 메시지가 쌓일 기간이 3주 이상 | 기능을 최소한으로 줄여야 함 |
| B. 12월 중순 출시 | 개발 여유가 생김 | 공유와 메시지 기간이 짧아짐 |
| C. 크리스마스 직전 출시 | 개발 기간이 가장 김 | 롤링페이퍼로서의 의미가 크게 줄어듦 |

**[추천] A.** 핵심 흐름(트리 생성 → 공유 → 메시지 → 개봉 → 캐릭터 획득)만 먼저 출시하고, 나머지는 운영하면서 추가한다.

**영향:** 기능 범위, 인증 방식(간단할수록 빠름), 디자인 에셋 제작 범위, 스택 선택(익숙한 쪽이 유리).

## 2. 포켓몬 IP 사용 범위

**왜 중요한가:** 디자인, 에셋, 데이터 구조, 서비스 이름, 저장소 공개 여부가 모두 여기에 달려 있다. 삭제 요청을 받으면 시즌 중에 서비스가 멈출 수 있다.

| 선택지 | 장점 | 단점·위험 |
|---|---|---|
| A. 공식 이미지·명칭 사용 (PokéAPI 등) | 팬 경험이 가장 좋고 에셋 제작이 필요 없음 | 권리 침해 위험, 삭제 요청 시 서비스 중단 가능 |
| B. 명칭·도감 번호만 사용, 이미지는 자체 제작 | 에셋 위험은 줄어듦 | 명칭·캐릭터 자체도 권리 대상일 수 있음, 그림 제작 부담 큼 |
| C. 오리지널 캐릭터 + 포켓몬 "감성"만 차용 | 법적 위험이 가장 낮음 | 팬 프로젝트로서의 매력이 줄어듦, 캐릭터 디자인 필요 |
| D. 교체 가능한 구조로 만들고 출시는 C, 판단 후 전환 | 위험 관리와 확장 모두 가능 | 추상화 작업이 조금 필요 |

**[추천] 이 결정은 법적 판단이 필요하므로 AI가 정하지 않는다.** 다만 어떤 선택을 하든 "캐릭터 팩"을 데이터로 분리하는 구조(D의 기반)를 먼저 만드는 것을 권한다. 삭제 요청이 와도 서비스를 유지하며 에셋만 바꿀 수 있다.

**영향:** 디자인 작업량, 이름·도메인, 저장소 공개 여부, 이미지 트래픽과 CDN 비용, 종료 후 에셋 관리.

## 3. 트리 소유자 인증 방식

**왜 중요한가:** 개인정보 수집 범위, 소유권 복구, 다중 트리 허용 여부, 개발 기간이 모두 이 결정에 달려 있다.

| 선택지 | 장점 | 단점 | 구현 난이도 |
|---|---|---|---|
| A. 비밀 관리 링크 (가입 없음) | 개인정보 거의 없음, 가장 빠름 | 링크를 잃으면 복구 불가 | 낮음 |
| B. 트리 이름 + 비밀번호 | 가입 없이 재접속 가능 | 비밀번호 저장 책임, 복구 어려움 | 낮음~중간 |
| C. 소셜 로그인 (카카오/구글) | 복구 쉬움, 다중 트리 관리 쉬움 | 개인정보 처리 의무 증가, 앱 심사·설정 시간 필요 | 중간 |

**[추천] 출시일이 12월 초라면 A 또는 B.** C는 복구가 편하지만 개인정보 처리방침과 OAuth 앱 설정에 시간이 든다.

**영향:** 개인정보 정책, Spring Security 구성, ERD(User 테이블 유무), 도감의 소속(사용자 단위인지 트리 단위인지).

## 4. 메시지 개봉과 캐릭터 지급 규칙

**왜 중요한가:** 서비스의 핵심 재미이자 재방문 동기다. 수집 요소가 롤링페이퍼 경험을 해치지 않게 설계해야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 받는 즉시 개봉 가능 | 즉각적인 재미, 단순함 | 크리스마스 당일의 특별함이 없음 |
| B. 크리스마스 당일 일괄 개봉 | 기대감이 크고 "선물" 컨셉에 맞음 | 그전까지 할 게 없어 재방문 동기가 약함 |
| C. 하이브리드: 수와 장식은 즉시 보이고, 내용은 당일 공개 | 기대감과 재방문 둘 다 확보 | 규칙 설명이 필요 |

**[추천] C를 우선 검토.** 캐릭터 지급은 서버에서 확정해야 한다(클라이언트에서 정하면 조작 가능).

**영향:** 출시일 압박(B와 C는 12/25 전 출시가 필수), 캐릭터 확률·중복 정책, 메시지가 적은 사용자 경험, 서버 로직.

## 5. 인프라 구조와 월 비용 상한

**왜 중요한가:** Spring Boot는 상시 실행되는 서버가 필요해 유휴 비용이 생긴다. 과거 비용 문제를 피하려면 상한을 먼저 정해야 한다.

| 선택지 | 특징 |
|---|---|
| A. 정적 FE(Netlify 등) + 소형 VM/컨테이너에 Spring + 저렴한 관리형 Postgres | 지금 뼈대를 그대로 씀. 상시 서버 비용 발생 |
| B. 정적 FE + 슬립 가능한 PaaS + 무료 티어 DB | 비용은 최소, 콜드 스타트·무료 티어 제한을 감수 |
| C. 백엔드를 BaaS(Supabase 등)로 대체 | 개발이 빠르고 비용 낮음, 기존 Spring 뼈대 폐기 |

**[추천] 수치는 아직 제시하지 않는다.** 서비스별 무료 티어와 가격은 2026-11 기준으로 조사한 뒤 비교표를 만든다. 먼저 **월 비용 상한**(예: 0원 / 1만원 / 3만원)과 **장애 허용 수준**만 정하면 된다.

**영향:** 기술 스택 유지 여부, 이미지 호스팅 방식(IP 결정과 연동), 백업과 종료 절차.
