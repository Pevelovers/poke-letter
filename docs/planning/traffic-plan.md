# 트래픽 대비 계획

> 2026-11-19 · 상태: **확정** (수치 가정은 12월 실측으로 보정)
> 관련: [인프라](infra.md), [일정](schedule.md), 정책 POL-OPS-05·06, 기능 F-OPS-08·09

## 왜 필요한가

비슷한 서비스 '내 트리를 꾸며줘'(2021)는 출시 5일 만에 가입 약 230만, 메시지 약 3,500만, **최대 동시 접속 약 117만**을 기록했다. 예상 서버비 10만 원이 약 2천만 원이 됐고 DoS 공격도 받았다 ([스브스뉴스 인터뷰](https://v.daum.net/v/VJ2CAHWQCL), [경향신문](https://www.khan.co.kr/article/202112231756011)).

PokeLetter는 지인의 EC2 한 대와 Supabase 무료 플랜(공유 CPU, RAM 500 MB, 전송량 월 5 GB)으로 시작한다. 그래서 **12월 중순까지의 실측 트래픽으로 12/24~25를 예측하고, 감당할 수 없으면 GCP 무료 크레딧으로 서버와 DB를 미리 옮긴다.**

## 1. 측정 (12/1 ~ 12/15)

매일 한 번 기록한다 (F-OPS-08). 개인정보 없이 집계 수치만 남긴다.

| 지표 | 출처 | 쓰는 곳 |
|---|---|---|
| 누적·일별 트리 수 (T) | DB 집계 | 12/25 개봉 부하 예측 |
| 누적·일별 메시지 수 (M) | DB 집계 | 12/24 작성 부하, DB 용량 예측 |
| 시간대별 요청 수, 최대 RPS(초당 요청) | 리버스 프록시 접근 로그 또는 actuator `http.server.requests` | 피크 배율 계산 |
| p95 응답 시간, 5xx 비율 | 위와 같음 | 한계 접근 여부 |
| 서버 CPU·메모리 | `docker stats`, `free -h` | 서버 한계 |
| DB 크기, DB 연결 수, Supabase 전송량 | Supabase 대시보드 Usage | 무료 한도 소진 예측 |

## 2. 용량 측정 (출시 직후, 12/2 ~ 12/5)

실제 운영 환경(EC2 + Supabase)에서 부하 테스트를 한 번 한다.

- 시나리오: 트리 보기(가장 많음) 70%, 메시지 작성 20%, 내 트리·메시지 열람 10%
- 결과: **C = p95 응답 1초 이하, 5xx 1% 미만을 유지하는 최대 RPS**
- 도구: 저장소 의존성을 늘리지 않는 외부 도구(예: Docker로 실행하는 k6). 도입할 때 확인한다
- 실행 시간: 사용자가 적은 새벽. 테스트 데이터는 끝나면 지운다
- 공격처럼 보이지 않도록 지인에게 미리 알린다 (같은 서버의 다른 서비스 영향)

## 3. 예측 (12/15)

12/1~15 실측값으로 아래 식을 채운다. **[가정]** 값은 실측 비율이 있으면 그것으로 바꾼다.

**12/24 (막판 작성)**
```
M_24 = 최근 7일 일평균 메시지 × α        [가정] α = 3 (전날 몰림)
RPS_24 = 최근 7일 최대 RPS × α
```

**12/25 00:00~01:00 (일괄 개봉)**
```
트리 수 T_25 = 현재 T + (최근 7일 일평균 신규 트리 × 남은 일수)
개봉 요청 수 = T_25 × p × r
RPS_25 = 개봉 요청 수 / 3600 × b
  [가정] p = 0.5  (첫 1시간 안에 여는 주인 비율)
  [가정] r = 20   (주인 1명의 요청 수: 내 트리, 메시지 페이지, 이미지 제외)
  [가정] b = 5    (1시간 평균 대비 0시 직후 몇 분의 순간 배율)
```

**DB와 전송량**
```
DB 크기(1/31) = 현재 크기 + 일평균 증가 × 남은 일수
전송량(12월)  = 12/1~15 전송량 × 2 × α
```

## 4. 판단 기준 (12/15)

아래 중 **하나라도** 해당하면 GCP로 옮긴다.

| 조건 | 기준 |
|---|---|
| 서버 | max(RPS_24, RPS_25) > **C × 0.5** (2배 여유) |
| DB 용량 | 1/31 예측 크기 > 500 MB × 0.7 |
| DB 전송량 | 12월 예측 > 5 GB × 0.7 |
| 실측 이상 | 12/15 이전에 p95 1초 초과나 5xx 1% 초과가 하루라도 있었음 |
| 서버 사정 | 지인 서버의 메모리 부족, 다른 서비스와 충돌, 재시작 권한 없음 |

해당하지 않으면 EC2 + Supabase를 유지한다. 단, 12/20까지는 같은 지표를 계속 보고 기준을 넘으면 그때 옮긴다 (리허설은 미리 끝내 둔다).

## 5. GCP 이전 준비 ("미리 진행")

이전 여부와 상관없이 **12/12까지 리허설을 끝내 둔다.** 그래야 12/15에 결정한 뒤 바로 옮길 수 있다.

### 대상 구성

| 구성 | 선택 | 이유 |
|---|---|---|
| 리전 | `asia-northeast3` (서울) | 사용자와 가깝다 |
| 서버 | **Compute Engine VM + Docker** (EC2와 같은 방식) | 고정 외부 IP를 DuckDNS A 레코드에 그대로 넣을 수 있다. Cloud Run은 DuckDNS에 연결하려면 로드밸런서가 필요하고 콜드 스타트 문제가 있다 |
| DB | **Cloud SQL for PostgreSQL 18** | Supabase 무료 한도(RAM 500 MB, 전송량 5 GB)를 벗어난다. 백업도 자동이다 |
| 도메인 | `pokeletter.duckdns.org` 그대로 | **A 레코드 IP만 바꾸면 된다.** OAuth 리다이렉트 URI, 공유 링크가 그대로 동작한다 |
| 계정 | PokeLetter 구글 계정 (`pokeletter.contact@gmail.com`) | 서비스 계정을 한곳에 모은다 |

### 크레딧과 기간

- 신규 계정 **$300, 가입일부터 90일**. 소진과 90일 중 먼저 오는 쪽에 끝나고, 멈추거나 연장할 수 없다 ([공식 문서](https://docs.cloud.google.com/free/docs/free-cloud-features))
- 체험이 끝나면 자원이 정지되고, 30일 안에 유료 전환하지 않으면 삭제된다. 우리는 1/31에 종료하므로 유료 전환하지 않는다
- **가입 시점: 12/8 무렵** (리허설 시작). 90일 뒤 약 3/8이라 1/31 종료까지 덮는다. 너무 일찍 가입하면 기간만 줄어든다
- 크레딧은 2개월을 버티도록 쓴다. 평소에는 작은 사양, **12/23 ~ 12/26에만 큰 사양**으로 올렸다 내린다
- 예산 알림을 $100, $200, $270에 건다
- [확인 필요] 체험 계정의 동시 vCPU 상한 등 제한은 가입할 때 콘솔에서 확인한다

### 리허설 (12/8 ~ 12/12, 실제 전환 없이)

1. GCP 가입, 프로젝트, 예산 알림
2. VM 만들기 (Docker, 패치된 JDK 25 이미지, CVE-2026-114938 대응 IN-7·8 그대로 적용)
3. Cloud SQL 만들기, 운영 DB의 `pg_dump`를 복원해 보고 걸린 시간을 잰다
4. VM에서 앱을 띄워 Cloud SQL에 연결, 헬스 체크와 로그인을 확인한다 (임시 주소, DuckDNS는 바꾸지 않음)
5. 전환 절차서와 되돌리기 절차서를 실제 걸린 시간과 함께 적는다

### 전환 (결정 시 12/16 ~ 12/20, 사용자가 적은 새벽)

1. 공지 배너로 점검 시간을 미리 알린다 (F-OPS-03)
2. 쓰기 중지: 메시지 작성·트리 생성을 잠시 막는다 (F-OPS-09)
3. Supabase → Cloud SQL 최종 `pg_dump` / 복원, 행 수 비교
4. GCP 앱을 Cloud SQL로 띄우고 확인
5. DuckDNS A 레코드를 GCP VM IP로 바꾼다
6. 쓰기를 다시 연다. 로그인 세션은 서버 메모리에 있으므로 모두 다시 로그인해야 한다 (POL-ACC-03)
7. 되돌리기용으로 EC2 + Supabase를 48시간 그대로 둔다 (쓰기는 막아 둠). 문제가 생기면 A 레코드를 되돌린다

**12/21부터는 이전하지 않는다.** 12/23부터 배포를 멈추는 원칙(D-06)과 같은 이유다.
